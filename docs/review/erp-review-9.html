R9-01Two people (or two tabs) issuing the same draft invoice or credit memo at the same moment get two numbers, and a save landing during an issue changes an approved invoice or leaves its total out of step with its lines.Still openwas R8-01Invoices & moneyeffort MHigh
What happens

Sprint 3 did not touch the invoicing code; the mechanism is unchanged. Issuing reads the draft with a plain read, checks status and version in JavaScript, then writes keyed only on the id:

const invoice = await tx.invoice.findUnique({ where: { id }, include: { lines: true } });   // documents.ts:246
if (invoice.status !== "DRAFT") throw ...                                            // :248
if (invoice.version !== version) throw ...                                            // :249
const issued = await tx.invoice.update({ where: { id }, data: {
  invoiceNumber: await nextNumber(tx, INVOICE_COUNTER_KEY, ...),                          // :254
  status: "ISSUED", ... total: fromCents(totals.totalCents) ...

There is no SELECT ... FOR UPDATE on the invoice row and the update's where doesn't include status: "DRAFT" or the version. Under Postgres's default isolation (read committed) two transactions that start together both see DRAFT/version 1, both pass, and both draw a number from the counter. The draft save (PUT /api/invoices/:ref, invoices.ts:243-271) has the same read-check-write shape, and it deletes and rewrites the lines while issue recomputes the total from the lines it read earlier. Credit memos use identical code (documents.ts:354-376, invoices.ts:177-195).

Impact

Who: Accounting working the review queue (Invoices page, ~150 drafts a day), plus the Director, who also has Invoices edit. It needs two requests on the same draft within a few tens of milliseconds: two tabs open on the queue, two reviewers splitting the queue, or one person clicking Approve and issue in one tab while a Save from another tab is in flight. A single tab is protected by its busy flag. Rare per day, but it will happen over months, and every occurrence is wrong in the ledger.

  • Issue + issue: both users are told "issued" with different numbers. One number is burned: it exists only in the QuickBooks queue, and its push later goes DEAD with "Invoice INV-xxxxx no longer exists". Accounting has to explain a gap in the invoice sequence (auditors ask) and clear a dead sync row by hand. The approver recorded is whichever write landed last.
  • Save + issue: the approver confirmed one figure and a different one is stored and pushed to QuickBooks (an issued invoice changed after approval, without any audit row of the change), or the issued total disagrees with its own lines. A customer can be billed $125 on an invoice approved at $25, or receive an invoice whose lines add to $125 under a $25 total.

How it's noticed: not at the time - both users see success. Later as a DEAD row in the QuickBooks panel, a gap in numbers, or a customer querying a total.

Example
  1. SO-10452 ships 10 × BR-1001 at $2.50; the shipment raises a draft invoice for $25.00 (version 1).
  2. At 9:02:14 Dana (Accounting) and Lee (Director, covering the queue in another tab) both click Approve and issue on that draft.
  3. Both get 200. Dana's screen says INV-20002, Lee's says INV-20001. The database holds INV-20002; INV-20001 is queued for QuickBooks but points at nothing and dies with "no longer exists".
  4. Save + issue: Dana adds $100.00 freight and clicks Save while Lee approves the $25.00 draft. Both 200. Lee was told $25.00; the stored invoice reads $125.00 and that's what goes to QuickBooks (or, in the other interleaving, total $25.00 with lines adding to $125.00).
  5. Should have happened: the second request gets 409 "already issued / changed by someone else", and exactly one number is used.

Observed at the new head: issue+issue 5 of 5 rounds both 200 with different numbers (e.g. INV-20002 / INV-20001, stored INV-20002); 10 numbers drawn for 5 invoices; the worker then ran 10 rows: 5 done, 5 DEAD "Invoice INV-20001 no longer exists" (and 20003, 20005, 20007, 20009). Save+issue 8 of 8 both 200, issue response total $25 every time; stored total $125 in 6 rounds (changed after approval) and $25 with lines summing to $125.00 in 2 rounds. Credit memos 3 of 3 rounds both 200 with different numbers (CM-30002/CM-30001 etc.).

Fix

In issueInvoice, issueCreditMemo and both draft PUTs, lock the document row first: SELECT "version", "status" FROM "Invoice" WHERE id = $1 FOR UPDATE (as lockOrder does for orders), then re-check status and version. Alternatively claim with updateMany({ where: { id, status: 'DRAFT', version }, data: { version: { increment: 1 } } }) and treat count 0 as 409; draw the number only after the claim succeeds. Add issue+issue and save+issue race tests for invoices and credit memos (the probe above is a ready template).

R9-04A restart during a QuickBooks sync leaves those documents stuck as 'Sending…' forever, and two API processes running at once push the same invoices twice.Still openwas R8-05Invoices & moneyeffort MMedium
What happens

The worker reads due rows, then marks each one PROCESSING with an unconditional update before pushing:

const where = { system: SYSTEM, status: { in: ["PENDING", "FAILED"] }, nextAttemptAt: { lte: now } };  // :249
const rows = await prisma.syncOutbox.findMany({ where, ... take: 100 });
for (const row of rows) {
  await prisma.syncOutbox.update({ where: { id: row.id }, data: { status: "PROCESSING" } });   // :260

Nothing ever picks PROCESSING up again, and shutdown() only stops the timer and closes the HTTP server; an in-flight run is cut off by process.exit. The only guard against two runs is a module-level running flag, which protects one process only; the claim isn't conditional, so a second process that read the same PENDING rows pushes them too.

Impact

Who: Accounting, once QuickBooks is connected. Every deploy or restart has a chance of landing inside a run (a run of 100 rows takes tens of seconds against the real API). A rolling deploy or a second API process (two terminals, a PM2 cluster, an old process that didn't exit) doubles pushes.

Consequence: a stuck invoice never reaches QuickBooks and the customer is never billed there; the panel counts it as "1 queued" but lists nothing to retry, and the invoice pill reads "Sending…" indefinitely. Double pushes create the same invoice twice in QuickBooks unless the company file rejects duplicate numbers - a customer billed twice.

Example
  1. 4:55 pm: the worker starts a run with INV-20001..INV-20040 queued.
  2. 4:55:20: an admin restarts the API to deploy a fix while INV-20012 is being pushed.
  3. INV-20012 is left PROCESSING. A week later it still isn't in QuickBooks; the panel shows "1 queued · 0 retrying · 0 failed" and the problem list is empty; the invoice shows "Sending…".
  4. Separately, during a deploy the old and new processes overlap for a few seconds: both push INV-20003..INV-20006.
  5. Should have happened: rows claimed atomically by one worker; PROCESSING rows older than ~10 minutes requeued; shutdown waits for the run.

Observed: row set to PROCESSING, worker run with clock 7 days ahead: attempted 0; panel queue {pending 1, failed 0, dead 0}; problem list 0 rows; invoice sync status "PROCESSING"; fake QuickBooks invoices 0. Two worker instances (second module copy, overlapping by 200 ms, 6 queued invoices): worker 1 attempted 6, worker 2 attempted 4; createInvoice called twice for INV-20003, 20004, 20005, 20006 (two successful sync log rows each).

Fix

Claim rows atomically: UPDATE ... SET status='PROCESSING', claimedAt=now() WHERE id IN (SELECT id ... FOR UPDATE SKIP LOCKED) RETURNING *, or per row updateMany({ where: { id, status: { in: ['PENDING','FAILED'] } } }) and skip on count 0. At startup and every tick, requeue PROCESSING rows older than ~10 minutes. Make shutdown await the in-flight run (with a timeout). Before creating, skip if a link exists and look the document up by number. List PROCESSING rows in the panel with Retry. Document "run one API process" in the deploy notes.

05

Checked and found sound

What the passes tested directly and found working.

Ready to ship and reservations

Ready is Pick & Packed with readyAt set, so it holds stock. Reserved counts matched the Allocation rows in every probe; a short at the pack check releases exactly the short; un-ready keeps the packed quantities; cancelling a Ready order clears it and holds nothing.

Mark Shipped

Refuses an order with no pack check (409) and any quantity other than what was packed. Two Mark Shipped calls on one order, 6 rounds: always one 200 and one 409, never two shipments. The invoice is created in the same transaction; items are locked in id order, and a deadlock comes back as a 409 'try again'.

The claim's row lock

Claim against claim, 10 rounds: always exactly one winner. A live claim can't be taken (409 naming the holder), and an Admin can clear one.

Maker ≠ checker on the check itself

The check command refuses the order's writer (403 makerIsChecker), including orders entered before the upgrade. There's no other path to Checked.

Upgrade, otherwise

Orders that were only released or had only the pick list printed aren't marked ready, and the pack check treats them correctly. Carrier fields are safe when empty, the pickup date falls back to the ship date, and with no cost margin is left out rather than shown as 0% or 100%. The migrations match the schema exactly, and a non-superuser that owns the database can apply all 25.

Cost on the main reads

/api/items, /api/items/:id, the quick report and the Analytics summary strip cost and margin for logins outside the cost audience. The stripping happens after the shared cache, so the cache doesn't leak. Saving an item without cost leaves it alone, and catalog cost edits are audited.

Dock refusals

The dock login gets 403 on cancel, set-BOL, mark-printed, claim, unallocate, set-ship-date, order edit, invoices, the full customer list and vendor POs. Its order reads hide prices, and shipment invoice totals are null.

New routes and inputs

Every sprint 3 route has a permission guard. BOL defaults and carrier fields use strict schemas with length limits (a 51-character PRO gets 400). User text is rendered by React (no innerHTML anywhere), and CSV export neutralizes formulas.

PO receipts

Version-locked, over-receipt capped, Closed POs refused. Receive all outstanding only fills what is still owed, and it locks every received item before recomputing On PO.

Order Entry

Unknown items are refused by the server. Enter moves Item → Ordered → Rate → next line. Blank trailing rows are dropped, double submit is blocked, and a pasted header row is skipped. The duplicate P.O. warning ignores case, spacing and cancelled orders.
