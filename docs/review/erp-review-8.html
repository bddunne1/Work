Findings

Each finding cites file and line and gives a concrete failure case. Where several passes found the same problem it appears once, and 'Found by' lists them all. Findings marked 'reproduced' or 'confirmed' were demonstrated with probe tests against the real app on throwaway databases. Severity is for this setup: an internal network with about 15 users.

The common thread: sprint 2 added a review step between shipping and invoicing, but older paths still act as if the invoice is finished when the shipment is confirmed. Undo deletes or voids invoices without asking Accounting, the outbox assumes a push either succeeds or fails cleanly, and issue reads before it locks. Fix it in one place: an issued document can only change through the Invoices commands, and each command claims the row before it acts.
R8-01Saving and issuing the same draft at the same moment can issue an invoice whose total doesn't match its lines, or skip a numberInvoices & money · effort SHigh
Where
server/src/lib/documents.ts:245-266 (issueInvoice), :353-376 (issueCreditMemo); server/src/routes/invoices.ts:175-195, :243-270 (draft saves)
What happens
Issuing and saving a draft each read the document, check its status and version without locking the row, then write keyed only on the id. Under Postgres's default isolation, two requests that arrive together both pass the check. Probe tests against the real app reproduced it:
  • Two issues together (3 of 3 rounds): both return 200, and the two users are told different numbers (INV-20001 and INV-20002). The invoice ends up as INV-20002. INV-20001 is burned, and its queued QuickBooks push later fails as 'no longer exists'.
  • Save + issue together (adding $100 freight while approving; 12 of 12 rounds): both return 200. Either the issued invoice is changed after approval (the approver confirmed $25, and $125 is stored and pushed), or the issued total stays $25 while its lines add to $125.
Credit memos use the same code. All it takes is two tabs open on the review queue, or two people working it.
Fix
Lock the document row (SELECT … FOR UPDATE) at the start of issue and of both draft saves, then re-check status and version. Or claim it with updateMany({ where: { id, status: 'DRAFT', version } }) and treat a count of 0 as a 409. Only draw the number after the claim succeeds. Add issue+issue and save+issue race tests for invoices and credit memos.

R8-05A restart during a QuickBooks sync leaves those documents stuck; a second API process would push them twiceInvoices & money · effort MMedium
Where
server/src/integrations/sync.ts:247-260; server/src/index.ts:45-53; server/src/routes/integrations.ts:64; src/components/QuickBooksPanel.tsx:24
What happens
The worker marks a row PROCESSING before pushing, but only ever picks up PENDING and FAILED rows. Shutdown doesn't wait for an in-flight run. After a deploy restart mid-sync, the invoice never reaches QuickBooks and no retry is offered. The panel counts it as 'queued' and lists nothing, and the invoice reads 'Sending…' forever. Rows are claimed with a plain update, so two API processes (or an old one overlapping a new one) can both create the same invoice in QuickBooks.
Fix
Claim rows atomically (a conditional update, or FOR UPDATE SKIP LOCKED). Requeue PROCESSING rows older than about 10 minutes at startup and on every tick. Wait for the in-flight run on shutdown. Skip creating when a link exists, and look up by number first. Show stuck rows in the panel with Retry. Document 'one API process'.

04

Checked and found sound

What the passes looked at closely and didn't flag.

Reservation invariant

Every allocate, unallocate, release, ship, undo, cancel and back-order path calls syncReservations inside the same transaction. The probe tests found no path where Item.qtyReserved differs from the sum of its Allocation rows for orders created after the migration. Many concurrent allocations against one scarce item never over-commit it.

Lock ordering

Stock-moving commands lock items in sorted id order, so two orders sharing items can't deadlock each other.

Document arithmetic

Invoice and credit-memo totals are computed in integer cents with one rounding rule, and CHARGE lines (freight) are kept out of item quantities. The 2-decimal case matches the screen exactly.

QuickBooks connect

The OAuth state is random, single-use and expires after ten minutes, and the callback trusts only a state it issued. With TOKEN_ENCRYPTION_KEY set, tokens are sealed with AES-256-GCM and a fresh IV per write; without it they're stored as-is and the status endpoint says so, so set the key in production.

Sign-in

bcrypt hashes, throttled sign-in, a forced password change after an admin reset (with the token rotated), and permissions re-read on every request, so deactivation takes effect immediately.

Queries and errors

All raw SQL, including the new trigram search, is parameterized; sort keys come from a fixed list. The error handler maps Prisma's not-found and conflict errors to 404 and 409 and doesn't send stack traces.

Status commands

Each workflow step has its own endpoint with a version check, and the plain PUT only edits header fields and lines. Edits after Checked send the order back to Entered as designed.

Schema

prisma migrate diff shows no drift between the migrations and schema.prisma. The new indexes are used by the open-orders and search queries.

Method and caveats

  • The five passes: stock and the reservation table; invoices, credit memos and QuickBooks; security and permissions; screens; deploy, operations and tests. Each pass started from the known list and had to cite file and line and give a concrete failure case for every finding.
  • My checks: I checked the High and every Medium against the code myself, for example the unlocked read in issueInvoice, undo reversing the last shipment rather than the chosen one, the missing gate on the quick report, the warn-only secret check, the BACKORDERED backfill, and the Est. Ship and item-price bugs on the order screens. Duplicates across passes were merged (for example ACC-01, ACC-02 and OPS-01 became R8-01).
  • What was changed: nothing in the application. The passes sent only read requests to the running API. Probe tests ran on private scratch databases, which were dropped afterwards.
  • Not covered: a live QuickBooks sandbox (the outbox was exercised with the repo's fake QuickBooks client), and a fresh day-simulation run, which needs the generator fixed first.
  • Where things are: the known list is docs/review/open-bugs.md, which now lists this round's findings and status corrections.
